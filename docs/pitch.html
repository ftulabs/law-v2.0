An autonomous pipeline that takes an economy and a regulatory topic, searches the official government portals with no starting URL, reads what it finds — including scans — and maps each provision to an RDTII indicator with the exact quote attached.

Problem statement · 1 of 2

ESCAP measures how open the region is to digital trade.

What RDTII is
  • The Regional Digital Trade Integration Index — ESCAP's measure of how each economy regulates digital trade.
  • 12 pillars, 61 indicators. Each indicator is a legal question, answered with a citation to a real provision.
  • Used by governments to see where their rules sit against the region.
How it is built today
  • By hand. Analysts search each government portal, read the statutes, and record the article that answers each indicator.
  • Slow, expensive, and it ages the moment a law is amended.
  • Coverage is bounded by how many analyst-hours exist.
The index is only as current as the last person who read the gazette. That is the bottleneck this hackathon exists to attack.

  • Zone 2 — extraction. HTML, text PDFs and scanned PDFs. Character error rate under 5%.
  • Both pillars. All required economies. Exact CSV template.
What that rules out
  • Shipping a corpus we collected beforehand.
  • A lookup table of (economy, pillar) → known answer.
  • Skipping the documents that are hard to read.

The rules are written to stop the shortcut that would otherwise win: knowing the answer in advance.

The nature of the problem

It is not "read a PDF". It is four harder problems stacked.

  • You don't know where the law is. Every portal is a different machine, and the good ones are not indexed by Google.
  • The portals resist. Bot walls, JavaScript-only pages, an encrypted catalogue, pagination that ignores the page number.
  • An indicator maps to a provision, not a document. A 600-section Act is not an answer; section 26 is.
  • "Relevant" is a legal test, not a keyword. A ban and a conditional permission use the same words and mean the opposite.
And every one of those failures is silent. The run completes, the report says “no provision found”, and that is indistinguishable from an economy that genuinely has no such law. This is the single observation the whole design is built around.
How we approach it

If failure is silent, make everything measured.

Three rules we hold ourselves to
  • Every claim has a number behind it, or it is not claimed. Where nothing was measured, the app says “not measured here”.
  • Evidence is verbatim. The output carries the statute's own words and a link, so a reviewer can overrule the machine.
  • Uncertainty is routed, not hidden. Low confidence goes to a human queue instead of quietly into the submission.
Why this is the right shape

A policy researcher will not adopt a black box that outputs legal conclusions. They will adopt a tool that shows its working and is wrong in visible ways.

So the deliverable is not just the answer. It is the answer, the quote it came from, the test it was judged against, and how sure the system is.

Step 1 of 6

Discover — find the law without being told where it is.

Purpose & output
  • From (economy, pillar) only, produce candidate laws.
  • Output: title + official URL, tagged NEW when crawled live.
What we built
  • Site-scoped web search plus a per-portal adapter — each portal gets code that understands its own index.
  • 491 English indicator terms across all 61 indicators, plus native statutory phrases for Chinese and Mongolian.
What went wrong — and the fix
Malaysia's portal AES-encrypts its catalogue JSON. The adapter silently returned 0 Acts.
Decrypt with the key the page publishes itself.
Singapore's portal ignores the page number, so paging never advanced.
Enumerate by union of sort windows instead.
Australia's API only matches the Act title, not its text.
Query short, title-robust name fragments.
Still open — the sectoral tail. China's key cites ride-hailing, lending and credit instruments whose titles contain no data vocabulary at all; no query for “cross-border data transfer” will ever reach them. The fix is a sector sweep — more queries, not a new mechanism.
Step 2 of 6

Fetch — get the bytes past a portal that would rather you didn't.

Purpose & output
  • Turn a URL into the actual document body.
  • Output: cached bytes, de-duplicated by content hash.
What we built
  • A TLS-fingerprint-spoofing client, escalating to a real stealth browser only when a page turns out to be JavaScript-only.
  • Detect a single-page-app shell and suppress it rather than mapping navigation chrome as if it were law.
What went wrong — and the fix
Australia publishes large Acts as multi-volume compilations and 404s the single-file PDF.
Resolve every volume, then split per volume.
One portal answers "download": 0 — the operator saying no.
We do not engineer around it. We use a lane that permits us.
What that one fix was worth — the Telecommunications (Interception and Access) Act 1979 was yielding 1 provision instead of 618. The Telecommunications Act 1997: 0 instead of 1,377. Nothing had thrown an error.
Step 3 of 6

Read — including the documents that are pictures of text.

Purpose & output
  • Document → clean text, with the error rate measured, not assumed.
  • Output: text + a character error rate the run reports.
What we built
  • Detect a real text layer → copy it. No text layer → raster OCR.
  • Score the result against a human-checked transcript, every run.
  • Six engines, swappable from the main screen — each card states its cost, its speed and whether the page leaves the machine.

Step 4 of 6

Split — a citation is an article, not a document.

Purpose & output
  • Cut a statute into the unit an indicator actually maps to.
  • Output: article/section chunks, verbatim — never paraphrased, because the snippet column is the statute's text.
What we built
  • Per-country splitters. One shared regex was the wrong idea: Singapore numbers sections, Australia marks them by font weight.
  • Script-aware tokenising, so a language without spaces still indexes.
What went wrong — and the fix
Only a Mongolian law numbers articles N дүгээр зүйл. A ministry rule numbers clauses 1.1. — so every rule collapsed into one provision.
Recognise both forms. Measured on real documents: 1 → 29, 1 → 34, 1 → 25.
Keyword-shaped headings in Singapore turned out to be cross-references, not section starts.
Split on numbering only; strip portal chrome first.
Still open — some instruments have no numbering at all (a national programme's action plan is a table of measures). It extracts as one block. Arguably it is not law and should never have entered the corpus — which is the better fix.
Step 5 of 6

Match — decide whether a clause satisfies a legal test.

Purpose & output
  • Provision → indicator, with a reason a lawyer can argue with.
  • Output: quote + citation + rationale + source URL.
What we built
  • Hybrid retrieval — lexical + multilingual embeddings + reranking — to shortlist from tens of thousands of provisions.
  • The model is shown all sibling indicators at once, so it must choose between “ban” and “allowed on conditions” rather than pattern-match.
  • Small corpus → grade everything, so retrieval is a signal, never a gate.
Parameters were measured, not tuned by feel
383laws in the sweep corpus
36,590provisions
0.833→1.000provision recall, after the sweep

Two results were counter-intuitive and are recorded so nobody re-argues them: a law-level prefilter makes recall worse, and asking for three provisions per law degenerates into breadth without depth.

The bug that taught us the most — the tokeniser was [a-z0-9]+. For Chinese text it returned zero tokens, so every Chinese provision scored a flat 0.0 on the lexical half of the score — 65% of the ranking. Nothing threw. The run completed and reported “no provision found”.
Step 6 of 6

Score — say how sure we are, and never overstate it.

Purpose & output
  • Attach a confidence to every row, and route it.
  • Optionally rate how restrictive the law is (0 / 0.5 / 1), on the index's own scale.
Four signals, one number
  • Legal fit 0.40 — does it satisfy the test?
  • Search match 0.25 · Quote grounding 0.20 — is the quote really in the document?
  • Scope 0.15 — general rule or one sector? A sector-specific rule is capped, never auto-accepted.
What the number does
≥ 0.85accepted into the submission
0.60 – 0.85queued for a human check
< 0.60set aside, kept visible

A “no provision found” row is written explicitly, with the portal and terms searched. An indicator is never silently blank — an absence is a finding, and it is scored as one.

Being straight about this one — those weights and cut-offs are a reasoned judgement, not a fitted model. The next slide is why, and what it would take to fix.

Limitations · 1 of 4

The confidence score is not calibrated. It cannot be, yet.

What is actually true
  • 0.40 / 0.25 / 0.20 / 0.15 and the 0.85 / 0.60 cut-offs are a stated judgement.
  • The number is a relative ranking. It is not a probability, and we never print it as one.
Why we cannot fix it
  • No labelled dataset exists. The panel's database gives the answer — which law cites which indicator. It does not label (provision, indicator) → correct/incorrect, which is what fitting a weight requires.
  • A held-out set would need negatives too — provisions that look right and are not. Nobody has published those.
  • Generating them ourselves means the system grading its own homework.
What we did instead — made the number auditable rather than authoritative. Every row shows its four signals separately, the legal test it was judged against, and the quote — so a reviewer can overrule it in seconds. And anything under 0.85 is routed to a human by default.
Limitations · 2 of 4

There is nothing to benchmark against.

The gap
  • RDTII is compiled by hand. There is no published automated system doing this job.
  • So there is no baseline score, no shared evaluation harness, and no other team's numbers to sit beside ours.

“Provision recall 1.000” — good compared with what? We can only say it is better than our own previous configuration.

What we built to stand in for one
  • An evaluation harness that scores against the panel's own database, matching on portal URL first and instrument name second.
  • A parameter sweep, so choices are comparable to each other even when they cannot be compared to the field.

A measurement error we caught: Mongolia first scored 0 of 9. The key writes the law in English; the portal serves it in Mongolian. No string comparison bridges that — the scorer was wrong, not the run.

Limitations · 3 of 4

The biggest gap is discovery, not intelligence.

Round 1 — the missing tier
  • 10 of 37 cited laws are not Acts. They are regulator guidance, a licence condition, a statutory instrument, sectoral codes of practice.
  • We search Act portals. Those documents are not in an Act portal.
Round 2 — the same shape
  • India: the evidence is subordinate legislation — ministry and central-bank circulars as gazette PDFs. We are searching the right index for the wrong tier.
  • Mongolia: the catalogue is nine parts paperwork to one part statute.
Why it is not fixed — each tier needs its own enumerable index, and those indexes mostly do not exist. There is no API that lists “every code of practice a sector regulator has issued”. Closing it is a per-portal engineering cost, repeated per economy — not a model that needs to get smarter.
A Mongolian term taken from a dictionary rather than from the statute cost one run its entire document set. Twelve of seventeen documents were customs rules about processing goods abroad. Vocabulary must be measured against the portal's own index before it is trusted.
Limitations · 4 of 4

What we have not measured, said plainly.

  • Retrieval parameters were swept on English. The lexical side now runs on character bigrams for scripts without spaces. Whether the tuning still holds is unknown — and answerable with the sweep we already have.
  • The multilingual reranker has never been benchmarked. It is switched off for non-Latin economies rather than contributing noise. Safe is not the same as measured.
  • No OCR engine here reads Cyrillic or Lao. It has not mattered — China, India and Mongolia are all text. Thailand is where it starts to.
  • PaddleOCR is 10 minutes per page on CPU — 140× RapidOCR for the same accuracy. It is the intended reader for non-Latin script, and at that speed the plan does not hold as configured.
  • 52 of 61 indicators have never been scored. They run; nothing has checked that their definitions discriminate.
  • Nothing has been run twice on different days. Every number we show is a single reading.
Why we list these at all — a judge will find them. Better that we found them first, wrote them down, and can say exactly what each one would take to close.
